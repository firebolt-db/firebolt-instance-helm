This page shows how to enable TLS on the gateway and engine listeners.

`tls.gateway` and `tls.engine` each enable TLS independently, provisioned the same way as `auth.signingKeys` (see [Authentication](./authentication)): an existing `kubernetes.io/tls` Secret, or a chart-rendered cert-manager `Certificate`.

- `tls.gateway` terminates TLS on the gateway's client-facing listener (client → gateway).
- `tls.engine` enables TLS on the engine's query listener and, correspondingly, the gateway's connection to engines — including the active engine health check, which runs over the same connection.

They can be enabled independently or together.

### Values

```yaml
# my-values.yaml
tls:
  gateway:
    enabled: true
    existingSecret:
      secretRef: firebolt-gateway-tls # kubernetes.io/tls Secret: tls.crt, tls.key

  engine:
    enabled: true
    existingSecret:
      secretRef: firebolt-engine-tls # kubernetes.io/tls Secret: tls.crt, tls.key, ca.crt
```

<Note>
`tls.engine`'s Secret requires all three keys — `tls.crt`, `tls.key`, and `ca.crt` — even for a self-signed certificate with no separate CA (set `ca.crt` to a copy of `tls.crt` in that case). The engine's own internal health check and the gateway's upstream connection both need the issuing CA to validate the certificate independently of `tls.crt`.

The certificate's SANs must also cover every engine node's per-node hostname (`<release>-engine-<engine>-node-<i>-0.<release>-engine-<engine>-hl.<namespace>.svc.cluster.local`) and each Engine's ready-only serving hostname (`<release>-engine-<engine>-ready.<namespace>.svc.cluster.local`) — both the engine's self-health-check and the gateway's `auto_san_validation` verify against these names. A missing node SAN can leave the Engine `NotReady`. A missing serving-Service SAN can instead leave Engine pods ready while Gateway queries fail certificate verification. `tls.engine.certManager` derives these automatically; a BYO certificate has to include them explicitly.
</Note>

### Install

```bash
kubectl create secret tls firebolt-gateway-tls -n firebolt \
  --cert=gateway.crt --key=gateway.key

# ca.crt is required in addition to the standard tls.crt / tls.key keys.
kubectl create secret generic firebolt-engine-tls -n firebolt \
  --from-file=tls.crt=engine.crt --from-file=tls.key=engine.key --from-file=ca.crt=ca.crt

helm install firebolt ./helm \
  --namespace firebolt --create-namespace \
  -f my-values.yaml
```

### Upgrade from discovery-Service query routing

Older chart versions route Gateway queries through `…-hl`. This chart routes through `…-ready`, so existing Engine certificates must include the new serving hostname before the Gateway switches. This applies to both existing Secrets and cert-manager certificates. Helm does not wait for certificate reissuance or coordinate this transition.

For an existing TLS deployment, schedule a maintenance window and use this sequence:

1. Keep the old Gateway and chart configuration in place. Issue an Engine certificate containing the existing node and `…-hl` SANs plus `…-ready` for every Engine. For cert-manager, add these SANs to the existing Engine `Certificate` and wait for the replacement revision and Secret. Do not run an old-chart reconciliation that removes the added SANs during this step.
2. After the replacement Secret exists, restart all Engine StatefulSets and wait for their rollouts. The init container must rebuild the certificate chain. Check the certificate served by every node against both its node hostname and the new serving hostname.
3. Upgrade to this chart using the complete deployment values. The Gateway can now use the ready-only Service with certificates that already cover it.
4. Run `helm test` and verify SQL through the Gateway before ending the maintenance window. If certificate issuance or verification fails, leave the Gateway on the previous routing configuration.

For offline/GitOps deployments, stage the certificate resource or externally managed Secret, Engine restart, and chart upgrade as separate reconciliations. A successful `helm upgrade --wait` alone does not prove that the Gateway can query Engines using the new TLS identity. Preserve the old SANs while rollback to the previous chart remains possible.

### cert-manager as a certificate source

```yaml
tls:
  engine:
    enabled: true
    certManager:
      algorithm: RSA
      size: 2048
      issuerRef:
        name: internal-ca
        kind: ClusterIssuer

  gateway:
    enabled: true
    certManager:
      algorithm: RSA
      size: 2048
      dnsNames:
        - firebolt.example.com # the chart can't infer the externally-visible hostname
      issuerRef:
        name: internal-ca
        kind: ClusterIssuer
```

The engine's certificate's DNS names are derived automatically from every engine node's per-node hostname and each engine's internal service hostname — don't set `dnsNames` under `tls.engine.certManager`. The gateway's certificate has no such derivation; set `dnsNames` to whatever hostname clients use to reach the gateway.

<Note>
The issuer behind `tls.engine.certManager` must populate `ca.crt` in the Certificate's Secret, not just `tls.crt`/`tls.key`. CA and Vault issuers do this; a bare self-signed or ACME issuer may not. The chart's `tls-chain-setup` init container needs `ca.crt` to build the engine's own health-check trust bundle and fails the pod at startup if it's missing.
</Note>

### Renewal and restart procedure

Secret updates do not independently trigger Helm upgrades. Engines load serving certificates at startup, and their full certificate chain is assembled by an init container. Treat certificate replacement and workload restart as separate steps:

1. Renew or replace the certificate Secret, preserving its required keys and SANs. For cert-manager, wait for the replacement Certificate revision to be issued and its Secret to contain the new certificate. Merely observing an old `Ready=True` condition does not establish that renewal finished.
2. Restart affected workloads after the replacement Secret exists. For a same-CA Engine renewal, restart every Engine StatefulSet. For a Gateway serving-certificate change, restart the Gateway Deployment. If Engine CA trust changes, coordinate restarts of both Engines and the Gateway using a staged trust migration.
3. Wait for the rollouts, run the verified TLS hooks described below, and confirm the served certificate is the renewed certificate before its predecessor expires.

For the `firebolt` release in the `firebolt` namespace, restart Engine nodes one StatefulSet at a time during a maintenance window:

```bash
# Stop if discovery or any rollout fails.
set -e
workloads=$(kubectl get statefulsets --namespace firebolt \
  --selector app.kubernetes.io/instance=firebolt,firebolt/component=engine -o name)
for workload in $workloads; do
  kubectl rollout restart "$workload" --namespace firebolt
  kubectl rollout status "$workload" --namespace firebolt --timeout=10m
done
```

Run the loop in Bash. Waiting between nodes avoids initiating all restarts together, but does not guarantee uninterrupted distributed queries. Change the release and namespace in these examples to match your deployment.

After replacing a Gateway certificate, restart its Deployment:

```bash
kubectl rollout restart deployment/firebolt-gateway --namespace firebolt
kubectl rollout status deployment/firebolt-gateway --namespace firebolt --timeout=10m
```

Online Helm rendering hashes current auth/TLS Secrets as an additional rollout trigger. It cannot hash a future Secret that cert-manager has not issued yet. Offline rendering cannot read live Secrets. Neither mechanism watches for changes between Helm operations.

### Optional automatic restarts

If your platform already runs [Stakater Reloader](https://github.com/stakater/Reloader), you can opt workloads into Secret-triggered rollouts. The chart does not install Reloader. Its annotations belong on Deployment or StatefulSet metadata, not on pod metadata.

For example, enable Secret-triggered Gateway restarts through workload annotations:

```yaml
gateway:
  annotations:
    secret.reloader.stakater.com/auto: "true"
```

The same annotation can be set under `engineSpec.annotations` for Engine StatefulSets or `metadata.annotations` for the Metadata Service. Automatic reload watches referenced Secrets, including those updated by cert-manager. It does not stage CA trust changes, rotate database passwords, or coordinate signing-key promotion.

Each Engine node has its own single-replica StatefulSet. A shared Secret update can trigger concurrent restarts across those StatefulSets. Use manual restarts when you need to control that sequence. Reloader's rolling updates do not provide cross-node coordination or a query-availability guarantee. Configure annotation ownership and rollout strategy according to your Reloader and GitOps controller configuration.

A CA change requires overlapping trust and coordinated restarts. Do not replace the only trusted CA and both leaf certificates in a single upgrade. The chart does not automatically stage trust bundles or gate traffic cutover. Plan a maintenance window, or manage a separately validated staged migration outside the chart.

Enabling TLS on an existing plaintext release does not immediately close old plaintext listeners. During a rolling update, old Gateway pods can continue serving while replacement pods wait for certificates. Restrict external access during a security-posture change and verify that all old pods have terminated before restoring it. Engine TLS protocol changes also require a maintenance window because Engine and Gateway updates are independent.

### Verify certificate trust

When Engine TLS is enabled, `helm test` checks each Engine node against its node hostname and, when the Gateway is enabled, its ready-only serving hostname. These checks never disable certificate verification. To verify the Gateway as well, supply a certificate SAN as `serverName`. The test connects to the internal Service while verifying that hostname. For a private CA, supply a Secret containing `ca.crt`:

```yaml
tls:
  gateway:
    verification:
      serverName: firebolt.example.com
      caSecret: gateway-test-ca
```

Run all chart hooks after the rollout:

```bash
helm test firebolt --namespace firebolt --logs
```

An empty Gateway `serverName` skips its verified handshake test. Existing readiness and SQL hooks test functionality and do not establish Gateway certificate trust. The verified TLS hook projects only CA material and never mounts signing keys or TLS private keys.

### Caveats

- The `core-ui` sidecar (`engineSpec.uiSidecar`) follows `tls.engine.enabled` automatically, proxying to the engine over HTTPS without verifying its certificate — the connection is over loopback within the pod, so this doesn't need a trusted CA.
- cert-manager and its CRDs must already be installed in the cluster before `certManager` blocks are set on any value; the chart's `Certificate` resources otherwise fail to apply.
