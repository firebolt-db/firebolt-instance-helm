This page introduces the [`firebolt-instance` Helm chart](https://github.com/firebolt-db/firebolt-instance-helm) and the components it deploys on a Kubernetes cluster.

## Architecture

```text
        client ── HTTP ──▶  ┌────────────────────┐
                            │       Gateway      │
                            └─────────┬──────────┘
                                      │ routes by X-Firebolt-Engine
                                      ▼
                            ┌────────────────────┐      ┌────────────────┐
                            │      Engine        │ ───▶ │ Object Storage │
                            │  StatefulSet(s)    │      └────────────────┘
                            └─────────┬──────────┘
                                      ▼
                            ┌────────────────────┐
                            │  Metadata Service  │
                            └─────────┬──────────┘
                                      │
                                      ▼
                                  PostgreSQL
```

Each entry under `engines:` renders one 1-replica StatefulSet per node, plus a shared headless Service, ClusterIP Service, and ConfigMap.

## When to use the chart

The chart has no controller loop. Its running state is whatever the standard Kubernetes controllers maintain after `helm install`. That is enough for many deployments, including production ones, where engine sets are stable and changes go through a normal release cycle.

For day-2 operational capabilities such as zero-downtime engine rollouts, autoscaling, drift correction, and reusable per-engine templates, use the [Firebolt Kubernetes Operator](./operator-upgrade-path). The operator manages the same component set through CRDs and a reconciler. The two are complementary and built from the same engine and metadata image lineage.

## Upgrade behavior

The Gateway stops advertising readiness, waits five seconds for endpoint propagation, then closes query admission and waits for active connections. `gateway.terminationGracePeriodSeconds` bounds the whole shutdown (15 seconds by default). Requests still active at that deadline can be interrupted. A custom `gateway.podTemplate.lifecycle` replaces this default drain behavior.

Engine peer discovery uses a headless Service that publishes not-ready pods for bootstrap. The Gateway uses a separate `-ready` headless Service containing ready pods only, with active health checks in addition to Kubernetes readiness. Neither this filtering nor the Gateway's rolling update strategy coordinates Engine StatefulSet replacements. Engine upgrades and replica changes can interrupt queries.

When upgrading an existing TLS deployment, ensure your Engine certificate includes `<release>-engine-<name>-ready.<namespace>.svc.cluster.local` for every Engine before the Gateway switches to ready-only routing. Chart-managed Certificates include these SANs, but issuance and process restarts are separate operations. Use a maintenance window for the first transition, or pre-provision compatible certificate material and restart Engines before upgrading the Gateway.
